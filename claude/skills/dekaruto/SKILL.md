## プロジェクトファイル構成
各プロジェクトのファイルは以下の4つだけ:

1. `DOCUMENT.md` - **プロジェクトの本体ドキュメント（構想書）**。**ユーザーだけが書く**成果物であり、常にプロジェクトの中心（詳細は後述）
2. `CONTEXT.md` - Claudeが書く**文脈**: 背景 / 経緯・前提 / TODO（詳細は後述）
3. `RESEARCH.md` - Claudeが書く**調査の蓄積**: 疑問→調査結果のエントリ。未調査の疑問も含む（詳細は後述）
4. `LOG.md` - Claudeが別セッションで再開するための記録（ユーザーは基本読まない）

※旧構成（NOTES.md / TODO.md / SUMMARY.md / 旧CONTEXT.md / REFERENCES.md）は廃止。
  SUMMARY の役割は DOCUMENT.md 自体が果たす。

## DOCUMENT.md（本体ドキュメント）と CONTEXT.md / RESEARCH.md（素材置き場）

DOCUMENT.md はプロジェクトで一番大事なファイル。「不完全だけど進めるたびに充実していくドキュメント」であり、タスクはすべてこのドキュメントを完成させるために存在する、という位置づけにする。

### 執筆の完全分離（最重要ルール: 調査はClaude、執筆はユーザー）
- **DOCUMENT.md の内容を書くのはユーザーだけ。Claudeは一切書かない。**
  たたき台・移行時の初版・「整形だけ」も書かない。Claudeが作ってよいのは見出しだけの骨格（下記）まで
- Claudeの役割はレビューに限る: 事実確認（数字が古い・撤回済みの値を使っている等）、矛盾・抜けの指摘、TBDの棚卸し
- **Claudeの調査結果・データ・問答・分析はすべて CONTEXT.md / RESEARCH.md に書く。**
  ユーザーはこれらを素材に、自分の言葉で DOCUMENT を書く。この「素材→自分の言葉」の変換が理解の本体
- 背景: AI任せの執筆は理解と所有感を毀損することが実証されている（cognitive debt / comprehension debt。
  丸投げ型の理解度は質問型の6割程度、AI併用で理解テスト−17%等）。執筆の代行はユーザーの成長を助けない

### DOCUMENT.md の骨格（Claudeが作ってよいのはここまで）
プロジェクト開始時に以下の見出しを立てる。埋まっていない節には `（TBD）` と明記する。
**空欄の可視化自体が全体像の把握になる**ので、TBDを恐れず骨格を最初に全部作ること。

```markdown
# <テーマ名>
<!-- このファイルはユーザーだけが書く。素材は CONTEXT.md / RESEARCH.md -->

## 結論
（TBD）

## 目的・背景
（TBD）

## 全体像
（TBD）

## 論点と現時点の答え
（TBD）

## 未解決の問い
- （TBD）
```

- **結論は必ずドキュメントの冒頭に置く**のを推奨（仮の結論→確度の高い結論へ書き換えていく）。
  見出しの増減・構成はユーザーの自由

### CONTEXT.md の書き方（Claudeの担当範囲）
- プロジェクトの**文脈**を置く場所。セクション構成の目安（テーマに応じて調整可）:
  `## 背景` → `## 経緯・前提` → `## TODO`
- 背景・経緯は一度書いたら大きくは変わらない「静的な文脈」。再開時にまず読んで文脈を掴む入口にする
- **TODO** は「- [ ] ◯◯ → DOCUMENT「◯◯」を埋めるため」の形で DOCUMENT の節に紐付ける。
  紐付け先が書けないタスクは「本当に必要か？」を一度立ち止まって確認する
  （要調査系のTODOはここに書かず、RESEARCH.md の未調査エントリとして立てる）

### RESEARCH.md の書き方（Claudeの担当範囲）
- **「疑問→調査→答え」を1エントリ**として蓄積するファイル。調査結果・データ・参考リンクはすべてここに書く
- 会話の中でユーザーから出た疑問・仕様への問い・気づきは、まず疑問エントリとして立てる:

  ```markdown
  ## [yyyy-mm-dd] ◯◯の仕様はどうなっているか？
  （調査結果・データ・出典リンク）

  ## [yyyy-mm-dd] △△と□□はどちらが良いか？
  （未調査）
  ```

- まだ調べていない疑問は「（未調査）」のまま置いておく（未調査エントリの一覧が要調査TODOを兼ねる）
- 解消した疑問は消さずに回答を添えて残す（疑問の蓄積自体が理解の履歴になる）
- **調査結果の本文は常に最新の事実だけを残す**。間違いが判明した記述・新しい事実で置き換わった記述は
  消して書き直す（検討過程・撤回の履歴は LOG.md に残す。本文に取り消し線や旧版を積まない）

### 次のアクションはユーザーが決める
- **Claudeから「次はこうした方がいい」という提案・優先順位付けをしない。**
  次の一手を考えることが全体像の理解そのものであり、ユーザーの領分
- Claudeが行うのは、現在地の表示・事実の整理・選択肢の材料出しまで。
  そのうえで「どこから進めますか？」と開いた形で聞く（推奨マークや★を付けない）
- ユーザーから明示的に意見を求められた場合のみ、考えを述べてよい

### 現在地の表示
- **セッション開始時（再開時）**: DOCUMENT.md の目次と各節の充足状況（埋まった / TBD）を表示してから作業に入る。「地図を見てから歩く」
- **セッション終了時**: CONTEXT.md / RESEARCH.md に増えた素材を1〜3行で示し、「DOCUMENTに書きますか？」とユーザーの執筆を促す。
  書かない選択も尊重する（未反映の素材はCONTEXT/RESEARCHに残っているだけで、失われない）

### 既存プロジェクトの移行
- DOCUMENT.md が存在しない場合: 見出しだけの骨格を作成し、素材になりうる情報は CONTEXT.md / RESEARCH.md に整理する（DOCUMENTの中身は書かない）
- DOCUMENT.md が過去にClaudeが書いたものである場合: 内容を CONTEXT.md / RESEARCH.md へ移し、DOCUMENT.md を骨格に戻すことを提案する
- 旧構成ファイル（NOTES.md / TODO.md / SUMMARY.md / REFERENCES.md）が残っている場合:
  内容を振り分けて統合し（背景・経緯・TODO → CONTEXT.md、調査・素材・参考リンク・MEMO → RESEARCH.md）、旧ファイルの削除を提案する

## クイックキャプチャフロー (`/dekaruto quick <メモ>`)

雑に頭にあることを素早く記録するためのモード。対話を最小限にして、30秒以内に記録完了することを目指す。

1. 両ディレクトリの全プロジェクトのディレクトリ名と DOCUMENT.md（無ければ CONTEXT.md）を軽くスキャンし、メモの内容に最も関連しそうなプロジェクトを上位3件特定する
2. AskUserQuestion ツールで以下を提示:
   - 候補プロジェクト（最大3件）
   - 「新規プロジェクトとして作成する」
3. 選ばれたプロジェクトに対して以下を**確認なしで即座に**実行する:
   - `RESEARCH.md` に未調査エントリとして追記する:
     ```
     ## [yyyy-mm-dd] クイックキャプチャ（未整理・要深掘り）
     <メモ内容をそのまま記録>
     ```
   - `LOG.md` に1行だけ追記する:
     ```
     <!-- yyyymmdd クイックキャプチャ: <メモ冒頭20文字程度> -->
     ```
4. 完了を短く報告する: 「〇〇プロジェクトに記録しました。次のセッションで深掘りできます。」
5. それ以上の対話はしない（ユーザーが続けたい場合は話しかけてくる）

**新規プロジェクトが選ばれた場合:**
- テーマ名だけ質問し、保存先は「Google Driveに保存（非公開）」をデフォルトにして1問で済ませる
- ファイル作成後、上記3の記録を実行する

## セッションIDの記録（再開用）
LOG.md を更新する際は、必ず**冒頭1行目**に現在のセッション情報を記録します（既に行があれば上書き。履歴は残さず常に最新のみ）:

```
<!-- dekaruto-session: <session_id> | cwd: <セッション実行時のカレントディレクトリ> | updated: yyyy-mm-dd -->
```

session_id の取得方法（優先順）:
1. 自分のシステムプロンプトに記載された Scratchpad Directory のパスに含まれる UUID（`/private/tmp/claude-501/.../<UUID>/scratchpad` の `<UUID>` 部分）
2. 取れない場合: `ls -t ~/.claude/projects/$(pwd | sed 's|[/._]|-|g')/*.jsonl | head -1` の結果のファイル名（拡張子 `.jsonl` を除いた部分）

## 再開フロー
1. LOG.md 冒頭のセッション行（`<!-- dekaruto-session: ... -->`）を確認する
2. セッション行がある場合、セッションファイルの存在を確認する:
   `ls ~/.claude/projects/$(echo <cwd> | sed 's|[/._]|-|g')/<session_id>.jsonl`
3. セッションファイルが存在する場合、AskUserQuestion で以下を提示:
   - 「前回セッションを復元する（claude --resume）」
   - 「ファイルから要約して続行する（従来通り）」
4. 復元が選ばれた場合、実行環境を判定して以下の順で分岐する:
   - **herdr内**（`$HERDR_PANE_ID` が設定されている）: 右paneに分割して復元する
     1. `herdr pane split --current --direction right --cwd <cwd> --focus` を実行する
     2. 応答JSONの `result.pane.pane_id` から新しいpane IDを抽出する
        （`python3 -c "import json,sys; print(json.load(sys.stdin)['result']['pane']['pane_id'])"` 等で堅牢にパース）
     3. `herdr pane run <新pane_id> "cd '<cwd>' && claude --resume <session_id>"` を実行する
        （文字列全体は外側ダブルクォート、パスは内側シングルクォート）
     4. フォーク先で信頼確認（"Is this a project you created or one you trust?"）が出たら
        Enterで進めるようユーザーに伝える
   - **tmux内**（`$TMUX` が設定されている）: `tmux split-window -h -t $TMUX_PANE "cd <cwd> && claude --resume <session_id>"` で右ペインに起動する
   - **どちらでもない**: 「以下を実行してください」と `cd <cwd> && claude --resume <session_id>` を案内して終了する
   - ※ `--resume` は記録された cwd から実行する必要がある（セッションはディレクトリに紐づくため）
5. ファイルからの続行が選ばれた場合、またはセッション行がない・セッションファイルが消えている場合（従来フロー）:
   1. 全ファイル（DOCUMENT.md, CONTEXT.md, RESEARCH.md, LOG.md。旧構成ファイルが残っていればそれも）を読み込み
   2. DOCUMENT.md の現在地（目次と充足状況）を表示する（「現在地の表示」参照）。DOCUMENT.md がなければ移行を提案する
   3. 要約を表示: 「前回は〇〇まで進めました」
   4. 「どこから進めますか？」と開いた形で聞く（次のアクションの提案はしない。「次のアクションはユーザーが決める」参照）

## 検索機能
- 検索対象: テーマ名（ディレクトリ名）と DOCUMENT.md（旧構成のpjは SUMMARY.md）

### 検索の実装手順（必ずこの方法で検索すること）
1. Bash ツールで以下の両方を実行し、全プロジェクトのディレクトリ名一覧を取得する:
   - `ls /Users/kubotafumihiro/Git/dekaruto/project/` （gitディレクトリ）

2. 取得した一覧の中から、キーワードを含むディレクトリ名を部分一致でフィルタリングする
3. ディレクトリ名で見つからない場合は、Grep ツールで各プロジェクトの DOCUMENT.md / SUMMARY.md を両ディレクトリで検索する
4. 結果を AskUserQuestion ツールで提示する際、各項目にどちらのディレクトリか（git / Google Drive）を明記する

## 実行開始

コマンドの引数（`$ARGUMENTS`）と現在のディレクトリを確認し、上記のルールに従って動作してください。
